# 2026-10-22 Haiku 5.5 swap

Replacing `@cf/openai/gpt-oss-120b` (Workers AI) with `claude-haiku-5-5` on the direct Anthropic API for chat, tracker chat, screening, language detection, feed ranking, search strategy and career profile. This file collects the evidence in order. Plan: `~/.hermes/cache/scratch/ua/haiku-plan.md`.

## P0 probe

**Question.** Which request features does `claude-haiku-5-5` accept on the live API, so workers build against facts?

**What ran.** `evals/haiku-55-swap/probe.ts`, `npx tsx evals/haiku-55-swap/probe.ts`, on 2026-10-22 with `@anthropic-ai/sdk` 0.71.2 (`client.messages` and `client.beta.messages`; no raw fetch was needed, the SDK forwards `compaction`, `output_config` and `thinking.adaptive` untyped). Raw results: `evals/results/2026-10-22-haiku-55-swap/p0-probe.json` (signatures stripped, long strings cut, no headers). Fixtures are the public ads and constructed CVs in `evals/dataset` (14 EN, 2 DE).

**Cost.** Final run $0.0074 (message calls, at $0.10 / $0.50 per M). The probe ran three times while it was tuned, about $0.019 in all. `count_tokens` is free: its response is `{input_tokens}` only. The first two runs' raw files were overwritten by the third (same path); they had a one-sample effort test (easy prompt, all correct) and a coarser cache grid, and agree with the final run.

### Two findings that change the plan

1. **Compaction usage lives only in `usage.iterations`.** The compaction response has top-level `input_tokens: 0, output_tokens: 0`; the real 2,782 in and ~1,069 out are in `iterations[{type:'compaction'}]`. Every response also carries `iterations` and `output_tokens_details.thinking_tokens`. The ledger normalizer and the cost calc must sum `iterations` or compaction is billed but invisible. (Plan 2.3 had this; it's now confirmed.)
2. **The tokenizer is heavy on German.** Chars per token, measured with `count_tokens` on screening-style prompts (CV + ad + instructions):

| Text | Chars | Tokens | Chars/token |
|---|---|---|---|
| EN prompts, 14 cases | 120,658 | 39,394 | **3.06** (2.93 to 3.22) |
| DE prompts, 2 cases | 12,206 | 6,027 | **2.03** (2.00, 2.05) |
| EN CV alone | 1,703 | 703 | 2.42 |
| DE CV alone | 1,755 | 943 | 1.86 |
| EN ad alone | 4,489 | 1,424 | 3.15 |
| DE ad alone | 3,642 | 1,804 | 2.02 |
| JSON job list, 16 ads, compact | 59,141 | 20,702 | 2.86 |
| JSON job list, 16 ads, pretty | 59,718 | 20,991 | 2.85 |
| JSON job list, 14 EN ads | 51,709 | 17,070 | 3.03 |
| JSON job list, 2 DE ads | 7,433 | 3,634 | 2.05 |

   The plan's R = 2.5 chars/token is **not conservative for German** (2.0, down to 1.86 for CVs). English and JSON of English ads sit at 2.9 to 3.1. Set R from the worst measured text: **1.8** for anything that may be German, which makes the "over 60k tokens" count_tokens trigger fire at ~108k chars. Chat's worst case (~180k chars) is then ~100k tokens, so the in-loop guard has to be able to fire. Compact JSON and pretty JSON cost the same.

### What changed because of this

- Handed to W1 and the plan: no `temperature` anywhere; `thinking` is `adaptive` (default) or `disabled` (never at xhigh); effort map uses low/medium/high; min cache prefix 512; chars/token R is 1.8, not 2.5; usage must sum `iterations`; chat treats empty `content` as a failure; on-demand compaction works through SDK 0.71.2 `client.beta.messages` with an untyped cast, so Phase 2 needs no SDK bump.

## P0b caching probe

**Question.** For the cache layouts in `.claude/rules/prompt-caching.md`, what do `claude-haiku-5-5` and `claude-sonnet-5-5` really do?

**What ran.** `evals/haiku-55-swap/cache-probe.ts` (`npx tsx evals/haiku-55-swap/cache-probe.ts`, then `PROBES=3b npx tsx ...` for the thinking-change add-on), 2026-10-22, `@anthropic-ai/sdk` 0.71.2 with untyped casts. Request shape from `src/lib/models/anthropic.ts`: `thinking: {type:'adaptive'}`, `output_config: {effort:'low'}`, no temperature, one small tool. Every prefix is about 2.55k tokens (system block with an ad and a CV, plus the tool), over the 512 minimum, with a unique nonce so no probe reads another's entry. S = tools + system = 2,551 tokens (Haiku) / 2,552 (Sonnet). M = a 1,833-token message tail. Raw results (every attempt, usage, diagnostics, no key): `evals/results/2026-10-22-haiku-55-swap/p0b-cache-probe-2026-10-22T12-06-48-325Z.json` (probes 1 to 9) and `...T12-09-11-821Z.json` (3b).

**Cost.** $0.2998 in all: run 1 $0.2678 (Haiku $0.0165, Sonnet $0.2513, 102 calls), run 2 $0.0319 (14 calls). Cap was $0.90.

**Headline: the rules file is too cautious on effort and `tool_choice`.** On both models, changing `output_config.effort` or `tool_choice` (auto to none) invalidated nothing, not even the messages cache. Two rules need correcting (see the end).

### What this means for our design

1. **Pre-warm works** with adaptive thinking on both models, but only for sites without `output_config.format`. A format request writes a different entry (about 186 more tokens) than a no-format warm, so a format site can't be warmed by a plain `max_tokens: 0` call. Stagger those: first call, then the rest.
2. **Stagger on `message_start`, not completion,** for streamed first calls (2c). Parallel calls sent together all write and all pay (2a).
3. **Effort and `tool_choice` are free to vary within a prefix** on both models. Rule change: the "never vary effort per request within a site" and "don't switch to `tool_choice: none` for a final round" guidance is not needed on Haiku 5.5 and Sonnet 5.5 (probe 3). Sites can share a prefix across efforts. Keep the settings fixed per site anyway unless a measured gain needs a change.
4. **`thinking: disabled` on Haiku 5.5 is a different cache key for everything.** A site on `disabled` shares nothing with an adaptive site. Sonnet 5.5 won't take `disabled` at all.
5. **Mid-conversation `{"role":"system"}` messages work** on both models with no beta header and keep the earlier prefix. Use them for per-turn instructions as planned. The docs say not to put user input in a system message right after a tool result on these models; not probed here.
6. **Mixed TTLs work** (1h on tools+system, 5m automatic on the conversation) and the usage split shows it. The longer TTL must be first.
7. **Cache diagnostics work as documented** on both models and need no beta header. Wire `previous_message_id` into the per-site hit-rate logging.
8. **A shared CV block across call sites works** when model, tools and the bytes up to the marker match; site-specific text goes after the marker. Don't vary tool descriptions between sites.
9. Log the `cache_creation` TTL split per call (probe 5 shows it is populated), so 1h write cost is visible.

### Changed because of this

- `.claude/rules/prompt-caching.md` needs two edits (not made here, outside this step's file scope): the invalidation table says effort and `tool_choice` invalidate messages, and the Consequences list says never to switch to `tool_choice: none`. The probe shows neither invalidates anything on these two models; `thinking: disabled` on Haiku does invalidate everything. Also add: `output_config.format` changes the cache key.

## Effort eval

**Question.** Haiku 5.5 replaces gpt-oss-120b on seven call sites. Is it better, and at which effort level (no thinking, low, medium, high) should each site run?

### The answer

Haiku 5.5 beat gpt-oss-120b on every site where gpt-oss ran as the baseline. Screening answers fabricated a claim in 24 of 80 cases on gpt-oss and 1 of 80 on Haiku at medium. The tracker matched the expected action in 139 of 150 cases on Haiku medium and 48 of 150 on gpt-oss. Haiku is also faster and cheaper per call (screening p50 2.8 s against 8.8 s, $0.0008 against $0.0017). Final efforts: chat, language and search strategy at low; screening, tracker, ranking and career profile at medium. Nothing ran without thinking, because no thinking lost on every site that writes or states facts.

### What ran

- **Model and API.** `claude-haiku-5-5` on the direct Anthropic API, `@anthropic-ai/sdk` 1.1.0, API version 2026-10-21 (the P0 and P0b probes above used SDK 0.71.2). Every site ran through the shipped code (route handler, service or ranker), with only auth, the clock, the database rows and the rate limiter fixed. `temperature` is not sent.
- **Arms.** `haiku-low-nothink` (effort low, thinking disabled), `haiku-low`, `haiku-medium`, `haiku-high` (adaptive thinking), and `gptoss` (`@cf/openai/gpt-oss-120b` through a small Worker, `evals/haiku-55-swap/worker.ts`, on port 8799). The prompt-cache salt differs per arm and run, so arms never read each other's entries.
- **Graders.** Deterministic checks first. Where facts or quality are the question (screening claims, search strategy, career profile) an Opus 5.5 judge at high effort, clean context (no user rules, no skills), read every output. Ranking is scored with NDCG@10 against reference labels written once by Opus 5.5 (`evals/haiku-55-swap/fixtures/ranking-labels.json`).
- **Decision rule**, fixed before any paid run (`DECISION_RULE` in `evals/haiku-55-swap/lib/core.ts`): the lowest-effort Haiku arm that is within one failure of the best Haiku arm, has no more hard-constraint violations than gpt-oss (zero for ranking's top 10) and no errors the best arm didn't have. Overlapping Wilson intervals no longer qualify an arm. This was tightened before the paid runs, because at these sample sizes overlapping intervals let several extra failures through.
- **Command**, all on 2026-10-22: `npx tsx evals/haiku-55-swap/run.ts <site> --allow-anthropic-api --key-from-dev-vars [--gptoss-url http://localhost:8799] [--arms ...]`. Raw results, with the command, settings, rule, per-arm summary and every call, are in `evals/results/2026-10-22-haiku-55-swap/<site>/run-N.json`.

### What went wrong during the eval

1. **Search strategy run 1 scored nothing.** Every judge call failed with HTTP 400: the judge's JSON schema used integer `minimum` and `maximum`, which the API rejects. 35 or 36 of 36 cases per arm errored, so the "decision" in that file (low-nothink) is meaningless. Fixed by using enums (`c8101ea3`), and the E2E fake now rejects the same keywords (`ce22ca79`). Cost: $0.21 of generation.
2. **Search strategy run 2 judged the wrong thing.** The rubric penalised queries that don't carry a city name, but the product puts cities in the location parameter, not the query. Mean relevance sat at 3.2 to 3.4 on every arm. Fixed in the rubric (`6f51167c`), then run 3 ($3.50). Run 2 cost $3.77.
3. **Career profile invented claims on every arm.** Run 1: 12 to 17 of 36 cases on Haiku and 31 on gpt-oss, from wrong duration arithmetic, programming languages listed as working languages, invented aspirations and imprecise figures. `bb0e8239` computes durations in code, limits working languages to the CV's human languages and adds prompt rules. Run 2 measured it: 3 to 5 of 36.
4. **Language run 1 used the older grader.** The stricter grader (any fallback fails, English included) landed afterwards (`d5b829e5`). Run 1 counted only fallbacks on non-English documents, so its hard counts aren't comparable with later runs. No Haiku arm fell back at all. It was not rerun: it cost $0.11 and the winner can't change on a count of zero.
5. **A ranking run was stopped.** It had started with gpt-oss and incomplete labels: the labeller skipped one posting, and the old code threw away the whole label set. I stopped it before it wrote results and fixed the labeller to retry the missing postings (`9b8ad2fc`). Labels then cost $2.141. The stopped run's cost isn't in any file.
6. **gpt-oss was dropped mid-eval.** It's the slowest arm and never a candidate. It ran as the baseline on language, tracker, screening, career profile run 1 and search strategy run 1 (where the judge failed). Ranking, chat and the second runs are Haiku-only, and the hard-constraint limit became 0 there.
7. **Two prompts changed after their runs.** Screening run 1 predates the prompt fix `a8651b31`, so run 2 re-measured it. The tracker prompt changed in `69e7c7d7` (follow-up and prep now ask which application) after the tracker run, and the tracker was not rerun.
8. **The live check found a chat gap the eval didn't cover.** In the web UI an obvious pasted ad gets the app's buttons without a model call, so a typed question right after it reached the model as one merged user turn and got another application proposal. `6c762cbc` adds a per-turn note for that history shape (static prompt unchanged). Chat run 2 (low only, $0.08) re-measured the final prompt: 76/108 against 74/108 in run 1, zero unrequested writes, 90% cache hits.

### What changed

- `src/lib/models/haiku-effort.ts`: one fixed effort per site (chat, language and search strategy low; screening, tracker, ranking and career profile medium). `HAIKU_EFFORT_<SITE>` overrides it for evals.
- Career profile: durations computed in code, working languages limited to the CV's human languages, new prompt rules (`bb0e8239`).
- Per-site HTTP timeouts set at about four times the slowest production call in 60 days (45 s for chat, screening, tracker and language, 120 s for the feed sites), so a hung primary fails over in seconds instead of ten minutes (`ff43f679`).
- Eval harness fixes: judge schemas, rubric, label retry, stricter language grader (above). PR #176 carries the swap.
