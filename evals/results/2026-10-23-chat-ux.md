# Chat UX pass: German replies, reply length, screening offer, claims (2026-10-23)

**Question.** The 2026-10-22 Haiku 5.5 swap left four chat problems: English replies to German turns, replies over the 3-sentence target, the chat stating document and score facts it had not checked ("two emails", "ATS 80%" in production on 2026-10-23), and a compaction summary that wrote copied ad lines in English in a German chat. PR #182 changes the chat prompt and tools (and adds the `offer_screening_answers` tool for the new chip rule). Did the changes fix the four problems without breaking the rest?

## What ran

- **Harness.** `evals/chat-ux/` (new in this PR), built on the 2026-10-22 harness (`evals/haiku-55-swap/lib`). The real `/api/chat` POST handler with its tool handlers, a SQLite database built from `migrations/d1`, a fixed clock (Thursday 2026-10-22, Berlin), the signed-in eval user and 25 tracker rows. Since PR #179 the route owns history, so the site sends no `chatHistory`, writes no rows itself, and fails a turn unless the route stored exactly two rows.
- **Cases.** 34 turns in 9 conversations (`evals/chat-ux/fixtures/cases.ts`): 12 German turns with English ads, CVs and tool results; 8 English turns that tempt long answers; 9 screening turns (6 that bring up the form's questions, including the questions pasted as a list and a single form field pasted as it is, 3 that look close and are not); 4 claims turns (kit contents, ATS score) in English and German; 1 compaction turn on a seeded German history of about 108k characters.
- **Model.** `claude-haiku-5-5` on the direct Anthropic API at the shipped chat setting (effort low, adaptive thinking), `@anthropic-ai/sdk` 1.1.0, API version 2026-10-21. One arm, `haiku-low`, 3 runs per case. The cache is salted per run, so every run pays its own cold start.
- **Before and after.** Two runs of the same harness and the same final graders on two commits: **before** = `main` at `dd35d12f` plus the eval commits (recorded as `63343496`), **after** = the PR at `ad85a19c`. Run in parallel, 2026-10-23.
- **Commands.** In each worktree: `npx tsx evals/chat-ux/run.ts chat-ux --allow-anthropic-api --key-from-dev-vars --runs 3 --max-cost 1`. `--key-from-dev-vars` loads only `ANTHROPIC_API_KEY` from the main checkout's secrets file in-process and never prints it (approved by Wasim on 2026-10-23; `evals/haiku-55-swap/lib/key.ts`).
- **Raw results.** `evals/results/2026-10-23-chat-ux/`: `before/run-1.json` (first before run), `before/run-2.json` (the screening conversation again, for case s09 added later), `before/run-3.json` (final before), `after/run-1.json` (first after run, round-2 prompt at `274765f7`), `after/run-2.json` (final after), the console logs in `logs/` (as .txt, since the repo ignores *.log), and the regrades in `regrade/`.

## Grader changes made after seeing model output

Every check is a regex or a count, so a grader that is wrong moves the numbers. These changes landed after paid output existed; both arms in the final table were graded with the final version.

| Commit | Change | Seen in | Why it is a grader bug, not a relaxed bar |
|---|---|---|---|
| `51e92ee5` | **s03 reclassified** from a screening negative to a positive. s03 is "Why do you want to work at Nordhafen Handels? (max 600 characters)". | after run 1: the model offered screening 3 of 3 times | The prompt under test says questions from an application form get the screening offer, and a single form field pasted with its character limit is one. ## What the first after run found, and what changed because of it

The first after run (round-2 prompt) passed 70 of 102. Its failures drove one more prompt pass (agent-expert, one iteration, ruled on by Opus):

- **Times off by an hour.** Replies in g06 (run 3), g07 (run 2) and g08 (runs 2 and 3) "corrected" interview and follow-up times by one hour, for example "Ich muss außerdem meine frühere Antwort korrigieren: Fennel Labs ist am 28. Oktober um 14:00 Uhr ... nicht um 15:00". `get_applications` returned UTC instants and the clocks changed on 25 October, so the model converted them itself and got different answers in different turns. Every chat tool time now carries a `_local` wall-clock field in the user's time zone (`isoToWallClock`, DST-correct), and the prompt says to take times from it and never convert UTC.
- **A claimed write.** g07 run 2 said "Zapwerk steht jetzt auf abgelehnt" after calling only `get_applications`. The prompt now says a change is done only when its write tool returned ok this turn.
- **Length.** 20 replies over the cap: 9 closing questions or offers, 6 bulleted lists, 5 unprompted self-corrections, the rest advice with three or more reasons. The prompt now drops closing offers unless needed, caps advice at the answer plus two reasons, puts several items in one sentence, and allows a list only on request (never dropping items past 8).
- **German.** 1 of 51 German turns in English, a German question built around a quoted English line from the ad. Mixed-language messages are answered in the language of the user's own words.

## Conclusion

The PR fixes the four problems it targeted. German turns are answered in German every time (54 of 54, from 49), replies stay within 3 sentences 93% of the time (from 35%), the screening offer comes exactly when the form's questions come up (18 of 18, no false positives), no reply claims a document or score it was not given, and the compaction summary keeps the conversation's language. It is also faster and slightly cheaper per call, with a higher cache hit rate. Reply length is the remaining gap: 7 replies run one sentence over.

## Changed because of this

- `src/lib/agents/prompts/chat-prompt.ts`, `src/lib/agents/prompts/chat-compaction-prompt.ts`, `src/lib/agents/chat-tools/*` (PR #182): the rules above, the `_local` time fields and `offer_screening_answers`.
- The eval harness (`evals/chat-ux/`) stays in the repo as the regression check for these four areas; `evals/haiku-55-swap/sites/chat.ts` no longer double-writes history since #179.

## Follow-up: a language switch mid-conversation (2026-10-23, branch `fix/chat-language-switch`)

**Question.** After PR #182 shipped, production showed one shape the eval did not cover: an application whose whole conversation and kit were in English, then the user asked "Wie viele Dokumente hast du für diese Bewerbung schon erstellt?", and the reply came in English. Every German case above is German from its first turn. Does the reply follow the latest message when the user switches language, and what fixes it?

**What ran.** Six new cases (`evals/chat-ux/fixtures/cases.ts`, w01 to w06): conversation `switch-en-de` seeds four English exchanges about the open application, then three German turns (the production question first, then "what next" and an interview lookup); `switch-de-en` is the same in reverse. The English side is graded by a new `checkEnglish` (the mirror of `checkGerman`). Each arm ran those 6 plus the 12 German cases (g01 to g12) for regressions, 3 runs each, Haiku 5.5 low, same harness and graders: `npx tsx evals/chat-ux/run.ts chat-ux --allow-anthropic-api --key-from-dev-vars --runs 3 --cases w01,...,w06,g01,...,g12`. Before = `main` at `dc1adeed` (PR #182 merged) plus the eval cases (`bacb623f`); after = the same plus one per-turn state line (uncommitted when it ran, so the result files record `bacb623f`; it is the commit that follows it on the branch). Raw results: `language-switch/before-shipped.json`, `after-iteration-1.json`, `after-iteration-2.json`; logs in `logs/language-switch-*.txt`.

**The change.** The Style rule in the cached system prompt already says to reply in the language of the user's latest message, but it sits behind a whole conversation in one language. The fix repeats it as the last line of the per-turn state, which rides in a `role: system` message after the new message's cache marker, so the cached prefix is unchanged: "Reply language: the language of the user's own words in their latest message, even when the earlier turns and your earlier replies are in another language." It names no language, so it holds for any language a user writes in, and it defers to the Style rule's "own words" reading for pasted and mixed messages. No second model call: the only language detector in the app is a Haiku call.

| | Before (shipped) | After, iteration 1 | After, iteration 2 (same change, re-run) |
|---|---|---|---|
| Switch turns in the language of the latest message | 13 / 18 | **18 / 18** | **18 / 18** |
| English replies to English after a German conversation | 5 / 9 | 9 / 9 | 9 / 9 |
| German replies in German (switch and German cases) | 44 / 45 | 45 / 45 | 44 / 45 |
| German cases passed (all checks) | 36 / 36 | 31 / 36 | 30 / 36 |
| Replies within 3 sentences | 48 / 48 | 46 / 48 | 45 / 48 |
| No reply pointing at a button that is not shown | 53 / 54 | 48 / 54 | 52 / 54 |
| Cost | $0.0465 | $0.0499 | $0.0476 |

The switch misses on the shipped prompt were w03 run 1 (an English reply to a German question) and w05 runs 1 and 3, w06 runs 2 and 3 (German replies to English questions). The production question itself (w01) passed 3 of 3 here; the misses came on the turns after it.

**The German cases' drop is not a language problem.** Language held in all but one reply (g11, the German question built around a quoted English line from the ad, which also missed on the shipped prompt in PR #182's runs). The other failures are the length cap (one sentence over) and the button-mention check, mostly g12, a German "what can you do" answer that names a Button: it failed that check 3 of 9 times on the shipped prompt across PR #182's runs and 4 of 6 here. Across all runs of the shipped prompt (126 German-case turns), 8 ran over 3 sentences and 7 mentioned a button; with the fix (108), 5 and 8. Within run-to-run noise at these counts; worth watching on the next chat-ux run.

**Conclusion.** The state line fixes the switch: 18 of 18 in both runs, up from 13 of 18, at about 35 uncached input tokens per request and no cache cost.
