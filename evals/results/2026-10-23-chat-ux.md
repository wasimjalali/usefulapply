# Chat UX pass: German replies, reply length, screening offer, claims (2026-10-23)

**Question.** The 2026-10-22 Haiku 5.5 swap left four chat problems: English replies to German turns, replies over the 3-sentence target, the chat stating document and score facts it had not checked ("two emails", "ATS 80%" in production on 2026-10-23), and a compaction summary that wrote copied ad lines in English in a German chat. PR #182 changes the chat prompt and tools (and adds the `offer_screening_answers` tool for the new chip rule). Did the changes fix the four problems without breaking the rest?

## What ran

- **Harness.** `evals/chat-ux/` (new in this PR), built on the 2026-10-22 harness (`evals/haiku-55-swap/lib`). The real `/api/chat` POST handler with its tool handlers, a SQLite database built from `migrations/d1`, a fixed clock (Thursday 2026-10-22, Berlin), the signed-in eval user and 25 tracker rows. Since PR #179 the route owns history, so the site sends no `chatHistory`, writes no rows itself, and fails a turn unless the route stored exactly two rows.
- **Cases.** 34 turns in 9 conversations (`evals/chat-ux/fixtures/cases.ts`): 12 German turns with English ads, CVs and tool results; 8 English turns that tempt long answers; 9 screening turns (6 that bring up the form's questions, including the questions pasted as a list and a single form field pasted as it is, 3 that look close and are not); 4 claims turns (kit contents, ATS score) in English and German; 1 compaction turn on a seeded German history of about 108k characters.
- **Model.** `claude-haiku-5-5` on the direct Anthropic API at the shipped chat setting (effort low, adaptive thinking), `@anthropic-ai/sdk` 1.1.0, API version 2026-10-21. One arm, `haiku-low`, 3 runs per case. The cache is salted per run, so every run pays its own cold start.
- **Before and after.** Two runs of the same harness and the same final graders on two commits: **before** = `main` at `dd35d12f` plus the eval commits (recorded as `63343496`), **after** = the PR at `ad85a19c`. Run in parallel, 2026-10-23.
- **Commands.** In each worktree: `npx tsx evals/chat-ux/run.ts chat-ux --allow-anthropic-api --key-from-dev-vars --runs 3 --max-cost 1`. `--key-from-dev-vars` loads only `ANTHROPIC_API_KEY` from the main checkout's secrets file in-process and never prints it (approved by Wasim on 2026-10-23; `evals/haiku-55-swap/lib/key.ts`).
- **Raw results.** `evals/results/2026-10-23-chat-ux/`: `before/run-1.json` (first before run), `before/run-2.json` (the screening conversation again, for case s09 added later), `before/run-3.json` (final before), `after/run-1.json` (first after run, round-2 prompt at `274765f7`), `after/run-2.json` (final after), the console logs in `logs/` (as .txt, since the repo ignores *.log), and the regrades in `regrade/`.

## Grader changes made after seeing model output

Every check is a regex or a count, so a grader that is wrong moves the numbers. These changes landed after paid output existed; both arms in the final table were graded with the final version.

| Commit | Change | Seen in | Why it is a grader bug, not a relaxed bar |
|---|---|---|---|
| `51e92ee5` | **s03 reclassified** from a screening negative to a positive. s03 is "Why do you want to work at Nordhafen Handels? (max 600 characters)". | after run 1: the model offered screening 3 of 3 times | The prompt under test says questions from an application form get the screening offer, and a single form field pasted with its character limit is one. In the product the client routes such a paste straight to screening when the CV is tailored. The case expected the opposite of the instruction it was testing. This change cost the before arm 3 passes (it never offers screening) and gave the after arm 3. |
| `51e92ee5` | **Document counts checked per sentence, negation exempt.** "both emails" was matched anywhere in the reply. | after run 1, k01: "The cover letter and both emails (application and follow-up) haven't been generated yet." | That sentence is true and is the honest answer the case wants; the count pattern failed it for naming the documents it said were missing. A count stated as present still fails. |
| `51e92ee5` | **A button the next step brings is not a ghost.** A sentence about a button with "then", "once", "after", "dann", "sobald" is allowed when the response has no chip. | after run 1, g01: "Füg die Anzeige noch einmal ein, dann bekommst du den Button für den Fit-Check" | The prompt tells the model exactly that: once the buttons are gone, paste the ad again. The rule is "never point at a button that is not there", and this one comes with the next step. |
| `a2bd9d94` | **Stricter**: document claims caught in lists and past tense ("includes the CV, cover letter and emails", "was written"), copied text lines and every summary line graded for language, dotted German dates ("27.10.") not counted as sentence ends. | Sonnet's round-3 review of the graders, after the first before run | Holes in the graders that let false claims and English summary lines pass, plus one false failure on German dates. |

## What the first after run found, and what changed because of it

The first after run (round-2 prompt) passed 70 of 102. Its failures drove one more prompt pass (agent-expert, one iteration, ruled on by Opus):

- **Times off by an hour.** Replies in g06 (run 3), g07 (run 2) and g08 (runs 2 and 3) "corrected" interview and follow-up times by one hour, for example "Ich muss außerdem meine frühere Antwort korrigieren: Fennel Labs ist am 28. Oktober um 14:00 Uhr ... nicht um 15:00". `get_applications` returned UTC instants and the clocks changed on 25 October, so the model converted them itself and got different answers in different turns. Every chat tool time now carries a `_local` wall-clock field in the user's time zone (`isoToWallClock`, DST-correct), and the prompt says to take times from it and never convert UTC.
- **A claimed write.** g07 run 2 said "Zapwerk steht jetzt auf abgelehnt" after calling only `get_applications`. The prompt now says a change is done only when its write tool returned ok this turn.
- **Length.** 20 replies over the cap: 9 closing questions or offers, 6 bulleted lists, 5 unprompted self-corrections, the rest advice with three or more reasons. The prompt now drops closing offers unless needed, caps advice at the answer plus two reasons, puts several items in one sentence, and allows a list only on request (never dropping items past 8).
- **German.** 1 of 51 German turns in English, a German question built around a quoted English line from the ad. Mixed-language messages are answered in the language of the user's own words.

## Conclusion

The PR fixes the four problems it targeted. German turns are answered in German every time (54 of 54, from 49), replies stay within 3 sentences 93% of the time (from 35%), the screening offer comes exactly when the form's questions come up (18 of 18, no false positives), no reply claims a document or score it was not given, and the compaction summary keeps the conversation's language. It is also faster and slightly cheaper per call, with a higher cache hit rate. Reply length is the remaining gap: 7 replies run one sentence over.

## Changed because of this

- `src/lib/agents/prompts/chat-prompt.ts`, `src/lib/agents/prompts/chat-compaction-prompt.ts`, `src/lib/agents/chat-tools/*` (PR #182): the rules above, the `_local` time fields and `offer_screening_answers`.
- The eval harness (`evals/chat-ux/`) stays in the repo as the regression check for these four areas (and, since PR #183, a language switch mid-conversation); `evals/haiku-55-swap/sites/chat.ts` no longer double-writes history since #179.

## Follow-up: a language switch mid-conversation (2026-10-23, PR #183)

**Question.** After PR #182 shipped, production showed one shape the eval did not cover: an application whose whole conversation and kit were in English, then the user asked "Wie viele Dokumente hast du für diese Bewerbung schon erstellt?", and the reply came in English. Every German case above is German from its first turn. Does the reply follow the latest message when the user switches language, and what fixes it?

**Cases.** Twelve new turns (`evals/chat-ux/fixtures/cases.ts`, w01 to w12), graded by `checkGerman` and a new `checkEnglish`:
- `switch-en-de` (w01 to w03): four English exchanges about the open application are seeded, then three German turns: the production question, "what next", and an interview lookup.
- `switch-de-en` (w04 to w06): the same in reverse.
- `switch-fallback` (w07 to w10), after the German history: the form's six English questions pasted with no words of the user's own (expect German), "ok" (expect German), "Bitte antworte mir ab jetzt auf Englisch." (expect English), then a German question (expect English: the request holds).
- `switch-not-a-request` (w11, w12), added after the second review, after the German history: "Schreib mir das Anschreiben bitte auf Englisch." and a German question quoting a recruiter's "Please reply in English". Both expect German: asking for a document in English, or quoting someone, is not a request to change the chat's language.

**What ran.** Haiku 5.5 low, 3 runs, the same harness and graders on both arms. Every outcome records a hash of the chat prompt file it ran against (`output.promptHash`), so a result is tied to the prompt bytes, not only to the commit.
- **Before:** `main` at `dc1adeed` (PR #182 merged) with this PR's eval files, the 10 switch cases plus the 12 German cases: `npx tsx evals/chat-ux/run.ts chat-ux --allow-anthropic-api --key-from-dev-vars --runs 3 --max-cost 0.5 --cases w01,w02,w03,w04,w05,w06,w07,w08,w09,w10,g01,g02,g03,g04,g05,g06,g07,g08,g09,g10,g11,g12`. Raw: `language-switch/before-round2-shipped.json` (prompt hash `dcab5087508e`).
- **After:** this PR at `ca1e1fbd`, all 44 cases: `npx tsx evals/chat-ux/run.ts chat-ux --allow-anthropic-api --key-from-dev-vars --runs 3 --max-cost 1`. Raw: `language-switch/after-round2-full.json` (prompt hash `e32534f20f31`).
- **After, round 3** (the line that ships): the 12 switch cases plus the 12 German cases, 5 runs: `npx tsx evals/chat-ux/run.ts chat-ux --allow-anthropic-api --key-from-dev-vars --runs 5 --max-cost 0.3 --cases w01,...,w12,g01,...,g12`. Raw: `language-switch/after-round3-core-first.json` (prompt hash `a3387ce15936`), plus a 5-run recheck of w08 to w11 in `after-round3-core-first-w08-w11.json`. The rejected round-3 wording (see below) is `after-round3-request-first.json` (hash `3223ebe8c7f1`, 3 runs).
- Logs: `logs/language-switch-*.txt`. The first round's runs (6 switch cases, before review) are kept as `language-switch/before-shipped.json`, `after-iteration-1.json` and `after-iteration-2.json`; their after files record `bacb623f` because the change was not committed yet, which is why the later runs record the prompt hash. The raw files keep local paths and the eval's own profile ids on purpose: they are the run as it happened, with no user data in them.

**The change.** The Style rule in the cached system prompt already says to reply in the language of the user's latest message, but it sits behind a whole conversation in one language. The fix repeats it as the last line of the per-turn state, which rides in a `role: system` message after the new message's cache marker, so the cached prefix is unchanged. The line that ships: "Reply language: the language of the user's own words in their latest message, even when earlier turns are in another language. If the latest message has no words of their own (only pasted text, "ok", a name or a link), keep the language they have been typing in, or the pasted text's if they haven't typed yet. One exception: if the user, in their own words, asked you to reply to them in a particular language, keep replying in it until they ask for another. A document, a translation, a line they quote from someone else or text between << >> is not such a request." It names no language. No extra model call (the only language detector in the app is a Haiku call). The Style rule gained the same exception, so the two say one rule; that rewrites the 1h system cache once at deploy.

How it got there, in three rounds of review:
- **Round 1** had only the core rule, with no fallback, and reversed the Style rule for a bare paste. The Opus review caught it; w07 to w10 were added.
- **Round 2** (`ca1e1fbd`, the "After" column below) put "if the user asked for a reply language, keep using it" first. The Opus review rated that high: a request for an English cover letter, or a quoted "Please reply in English", would switch the chat for good. w11 and w12 test it.
- **Round 3** narrowed the request to the user's own words about the chat and excluded documents, translations, quotes and `<< >>` text. Put first, as before, it cost switch turns: 26 / 30 on w01 to w10 (w03 run 3, w06 runs 2 and 3, and w08 run 2's "Alles klar.", which the grader cannot score at two words). Moved last, as one exception after the core rule, it ships.
