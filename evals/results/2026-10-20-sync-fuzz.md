# Browser/server sync: randomized interleaving test (PR #155, review rounds 2 and 3)

Date: 2026-10-20. Branch `feature/mcp-data-integrity`.

## Question

Round 2: Codex found four races in `src/lib/session-sync.ts` between server updates and local
edits, and point fixes kept opening new edges, so the module was restructured around one door for
server content. Round 3: Codex and Opus found three more high-severity bugs in that restructure.
The test asks two things: does the engine hold under arbitrary interleavings, and does the test
fail on the code that had each bug (so it can be trusted to catch the next one).

## What ran

- Harness: `e2e/tools/sync-fuzz.ts` and `e2e/tools/sync-fuzz/` (store level, no browser). Command:
  `npm run test:sync` (tsx with `e2e/tools/tsconfig.sync-fuzz.json`). Flags: `--engine new|round2|legacy`,
  `--seeds`, `--from`, `--ops`, `--seed N --verbose`, `--only op,op` (isolate one bug), `--out file.json`.
  A bad flag or a crash exits non-zero and prints its message.
- Engines: `new` is `src/lib/session-sync-engine.ts` with the app's glue. `round2` is the engine,
  glue and server model of review round 2 (`e2e/tools/legacy/session-sync-engine.round2.ts`), and
  `legacy` is the round-1 module (`e2e/tools/legacy/session-sync.round1.ts`). Both legacy files carry a
  "TEST ONLY, do not import" banner.
- World: a fake server with revisions and per-field values, two tabs each with its own engine and
  store, and an agent. Requests reach the server and are answered in random order; each is on time,
  lost before the server, answered with an error after the server applied it, never answered (the
  caller's timeout fires on a manual clock) or late.
- What the faithful harness added in round 3:
  - `workflow_complete` results that carry the generated fields and arrive late; the glue of each
    variant is in the adapter (round 2 installed the fields into the store, then refreshed);
  - editor drafts that keep changing while a save is in flight, and the close-or-keep decision after it;
  - writes that do not bump the revision: workflow state, and in the round-2 server model the silent
    `requirements` annotation by regenerate and follow-up;
  - multi-column groups: the CV with its embedded structured data and screening answers, the email
    with its derived subject and body, the fit assessment, the tracker status;
  - Restore and Copy clicked on random notices of a tab, including old ones;
  - re-opening an application the tab already holds (an explicit load of an equal or older row).

Invariants, checked after every step and at quiescence:

| | |
|--|--|
| I1 | No lost edit. The last thing typed into a field is on the server, or in a conflict buffer with a notice raised, or still unsaved because the server refused it and the user was told. An editor told "saved" has its exact draft on the server and never closes over text typed during the save. Text set aside in a conflict buffer reaches the server only when the user restored the notice that names it, and Copy offers only the text of its own notice. |
| I2 | No stale overwrite. Every baseline is a truthful snapshot of the server at its revision and never moves backwards. A save only overwrites a server value its writer's store had shown (per part for the CV column, which holds several things). This is Opus's "a field's last accepted value must still be on the server or have been replaced by a writer that had seen it". |
| I3 | Convergence. At quiescence every store equals the server row (except values the server refuses), every tab's status is the server's, and every baseline is the server's revision. |
| I4 | No loops. The settle phase reaches a fixed point and a second pass raises no notice and makes no write. |
| I5 | A refused field never blocks the others and is listed as rejected rather than dropped. |

Ten deterministic cases (same world, requests driven by hand): Codex 1 to 4 (round 2), the
refused-field poll block, round 1's h2, and the three round 3 bugs plus the feed mapper parity.

## What the harness found in the fixes

Making the harness faithful turned up problems in the first version of the round 3 fixes, which were
fixed before the numbers above were taken:

- Dropping a group's conflict entry on any later save of the group lost text in groups that hold several
  things (the CV column holds the structured CV and the screening answers): a save of the title settled
  the screening text. Entries now go only when a save puts exactly their text on the server, or when restored.
- Replacing the group's entry on a second conflict lost the first conflict's text. Entries are now kept
  per conflict (at most 40 per application), so every notice's text stays reachable.
- Restore of an old notice overwrote text typed since, and text for a field the server had changed
  again since the notice. It now applies a property only where the user has not typed since and the server
  has not moved since the entry; otherwise the entry stays and a new notice says so.

## Conclusion and what changed

- `workflow_complete` no longer writes generated fields into the store for a stored application; it asks
  for the saved row (`refreshFromServer`), the same as regenerate, follow-up and tracker status. Anonymous
  and unsaved sessions keep the direct install. Fit-analysis results and chat-tool effects stay local edits:
  the server does not persist those fields, so they go through the revisioned save.
- Editor saves compare the draft sent with the draft now (`editorShouldClose`): if the user typed during
  the save the editor stays open with the newer text, based on the revision just saved.
- Each notice carries its own entry ids; Copy and Restore act only on those. Restore goes through the
  normal save path and never overwrites text the user has not seen.
- Lows: regenerate and follow-up now bump the revision when they annotate `requirements`; the feed
  handoff mapper builds on the standard mapper; a refused insert is retried once before it is reported as
  `limit`; the single-flight join returns `matchedBy: 'session'`, documented on `EnqueueKitResult`.

Deviation from the written rule: a row at the SAME revision as the baseline is ignored for polls,
conflict reloads and mutation refreshes, but applied for hydration, opening and handoff (workflow-only
writes do not bump the revision, and a handoff exists to show them).

Cost: none (no model calls). Time: 2000 seeds run in about 17 s.
