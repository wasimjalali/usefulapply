# Sonnet 4.6 vs Sonnet 5.5 for the Useful Apply kit (2026-10-12)

Supersedes `2026-10-07-sonnet-46-vs-55.md`. That file was the Bedrock-era plan. Bedrock is no longer used for models, and both models ran on the Anthropic API this time.

Short version: Sonnet 5.5 at effort low is about 2.7 times faster per kit, 23% cheaper, and invents far less than Sonnet 4.6 on the same applicant data. It isn't clearly a better writer, and it has one reliability bug (double JSON in short emails) that is our parser's fault, not the model's. Decision: switch everything to Sonnet 5.5, effort low, with the fixes in section 9.

All numbers below come from files in `evals/results/2026-10-12-sonnet-eval/` (call it `R`) unless another file is named. Owner-case results appear only as aggregates. Raw owner outputs stay in the gitignored `evals/private/`.

## 1. Question

Should the Claude kit tasks and CV parsing (nine writing and analysis tasks plus parse_cv) move from Sonnet 4.6 to Sonnet 5.5?

Why it matters:

- Writing quality is the product's moat. A cover letter that reads like a template loses the user the interview.
- Grounding is mandatory. Every skill, number and claim must trace to the applicant's CV. One invented certification can cost someone a job offer.
- Bedrock is retired for models, and the Anthropic API credits are the budget for this. So the question is Anthropic API 4.6 against Anthropic API 5.5, same network path, fairer latency.
- Speed matters because a kit is 10 sequential-ish calls and users wait on it.

Decision rule, fixed before the run (from the 2026-10-07 plan): switch everything if 5.5 wins or ties on writing, fabrication is not higher, there are zero truncations, refusals or JSON failures, p95 kit latency is within +25%, and cost per kit is not higher. Switch some tasks if it wins on writing but loses on latency or on short extraction tasks. Don't switch on any rise in fabrication.

## 2. What ran

### Arms

| Arm | Folder | Model ID | Settings |
|---|---|---|---|
| A | `sonnet46-api` | `claude-sonnet-4-6` | Production-identical request: per-task `MODEL_CONFIGS` temperature and max_tokens, same system blocks and `cache_control`, JSON-only suffix, no thinking. Production prompts. |
| B-low | `sonnet55-low` | `claude-sonnet-5-5` | No temperature, `thinking: {type: "adaptive"}`, `output_config: {effort: "low"}`. `sonnet55` prompt variant. |
| B-medium | `sonnet55-medium` | `claude-sonnet-5-5` | Same, `effort: "medium"`. |
| C | `sonnet46-api__prompts-sonnet55` | `claude-sonnet-4-6` | Arm A's request shape on the `sonnet55` prompt variant. 16 synthetic cases only. Added to separate model effect from prompt effect. |
| B-low, B-medium on fixed inputs | `*__on-sonnet46-api` | `claude-sonnet-5-5` | `--inputs-from sonnet46-api`: reuse arm A's stored analysis (applicant, job, skill match, metrics), rerun parse_cv and the writing tasks. Isolates writing from extraction differences. |

Two modes, as in `evals/README.md`: **chain** (each arm runs the whole kit, so "what happens if we switch everywhere") and **fixed inputs** (writing only, same analysis for both models).

### Request-shape differences (`evals/lib/arms.ts`, `evals/lib/client.ts`)

- Sonnet 4.6 sends the production temperature (0.1 to 0.3 on extraction tasks, 0.4 to 0.6 on fit and writing tasks, per `evals/prompt-variants/sonnet55/CHANGES.md`). Sonnet 5.5 rejects non-default sampling, so no temperature, top_p or top_k are sent.
- Sonnet 5.5 uses adaptive thinking with an effort level. No prefill, no `tool_choice`, no server-side `fallbacks`. A refusal counts as a failure of that arm.
- `max_tokens` for 5.5 arms is max(4000, 4 x the production value), because thinking counts toward it and the new tokenizer uses more tokens: parse_cv 32768, extract_applicant 16384, parse_job 16384, skill_matching 8192, extract_metrics 8192, fit_assessment 4000, optimize_cv 40000, write_cover_letter 8192, write_email 4096, write_follow_up_email 4000. Arm A uses the production values.
- Above 16000 `max_tokens` (parse_cv, optimize_cv) the client streams with `messages.stream(...).finalMessage()`. Everything else is a plain `messages.create`.
- SDK: `@anthropic-ai/sdk` 0.71.2 (`package.json` `^0.71.2`, installed 0.71.2). It has no types for adaptive thinking or `output_config`, so the request is built as a plain object and cast. The SDK forwards the body unchanged.
- Prices used (`evals/lib/pricing.ts`, per million tokens): Sonnet 4.6 $3 in / $15 out, Sonnet 5.5 $2 / $10, Opus 5.5 $4 / $20, cache write 1.25x, cache read 0.1x. Costs below are computed from recorded token usage at these prices, not read from an invoice. Correction found in review after the run: Anthropic's price page lists Sonnet 5.5 cache reads at $0.10 per million (5% of input), not $0.20, so the 5.5 per-kit costs here are overstated by about $0.002 (21,900 cache-read tokens per kit). No conclusion changes.

### Prompt variants

Arm A runs production prompts. The 5.5 arms run `evals/prompt-variants/sonnet55/` (`--prompt-variant sonnet55`), written from the migration guidance in the Claude API skill: temperature intent moved into `<voice>` blocks, ALL-CAPS pressure language toned down (for example 94 to 7 emphasis tokens in the CV prompt), each rule stated once, no em dashes in the prompt's own prose, three plain bugs fixed (trailing comma in the CV schema sample, stale "Job Copilot" name, dangling "Rule 4d" reference). Every anti-hallucination rule was kept in substance. Extraction prompts, the JSON-only suffix and validator-enforced limits were not changed (`CHANGES.md`). Because the two models got different prompts, arm C exists.

### Reps

- Quality pass: 1 rep, 30 cases, concurrency 4. This feeds judges, deterministic scoring, cost and token numbers.
- Latency pass: 10 cases (4 owner, 6 synthetic: `own-01, own-06, own-11, own-13, syn-01, syn-04, syn-07, syn-10, syn-14, syn-15`) at reps 2 and 3, concurrency 1, one arm at a time. That is 20 clean kits per arm. Wall clock for the 20 kits: 4.6 took 2,987 s, 5.5-low 1,072 s, 5.5-medium 1,193 s (`log-latency-*.txt`).
- Smoke run (`evals/results/2026-10-12-smoke/`): one synthetic and one owner case per arm to check the wiring before the real run.

### Judges

- **Primary judge:** Claude Opus 5.5 (`claude-opus-5-5`), effort high, adaptive thinking, `output_config.format` JSON schema. Blind: it sees the ad, the source CV and two outputs labelled Output 1 and Output 2, never an arm name. Each pair is judged twice with positions swapped (seeded); if the passes disagree the pair is a tie. Rubric dimensions scored 1 to 5: grounding, specificity, voice, structure and length, language and formality. The rubric says any fabrication scores 1 on grounding and "normally decides the verdict". A document missing from an arm (a failed step) is an automatic loss without a judge call.
- **Re-judge:** GPT-6 Astra (`gpt-6-astra`) via Codex, reasoning effort xhigh, read-only, on a seeded 30% sample of the synthetic pairs for 4.6 vs 5.5-medium chain (24 packets). Brief: `R/rejudge/brief-sonnet46-api__vs__sonnet55-medium.md`. The answer key sits outside the folder Codex could read.
- **Critical analysis:** Fable 5.1 read the report, scores, calls and public judge files and wrote `R/critical-analysis-fable-5-1.md`. It ran before arm C, the fixed-inputs judging and the re-judge were finished, so where its text and the final files differ, this write-up uses the final files.

### What Fable 5.1 adjusted (`critical-analysis-fable-5-1.md`)

Fable checked the judge's claims by hand and pushed back on the headline:

- **The CV sweep is mostly a grounding verdict.** The rubric scores any fabrication as grounding 1 and lets that decide. 4.6's CV scored grounding 1 in all 32 synthetic passes. On specificity the CV gap is 3.4 vs 3.8, and on voice 2.6 vs 4.1 (4.6's bullets are padded, which Fable calls fair). So "30-0" means 4.6 invents things, not that 5.5 writes 30 times better.
- **The letter win is partly length.** The rubric asks for about 250 to 350 words while the product spec is a 250-word body. 4.6 writes about 206 words, 5.5 about 245. The longer letter won 31 of 32 passes against low and 26 of 32 against medium. For CVs the winner was the shorter output 32 of 32, so the judge isn't length-chasing in general.
- **On writing alone it's roughly even.** On a manual read of four letters (4.6 vs 5.5-medium), Fable scored writing 1-1-2 instead of 28-2: 5.5 wins one on prose and grounding, two on grounding with 4.6 reading slightly smoother, and 4.6 wins the German letter on prose (5.5 had a broken sentence and lifted a term from the ad). "5.5 is clearly more grounded; it is not clearly a better writer."
- **Style shift.** 5.5 writes an explicit gap disclaimer in 11 to 12 of 16 letters (4.6: 4), for example "I won't pretend to have 12-15 years". It's honest, but a hiring manager may read it as self-rejection. Neither prompt asks for it.
- **Email "wins" for 4.6 are largely auto-losses** from the double-JSON failure (section 7). Across all 30 kits, judged email pairs go to 5.5-low 14-10 and 5.5-medium 18-10 when the missing documents are excluded.
- **Low vs medium:** medium is not better at writing. It's slightly better on the two short JSON tasks, mostly through fewer retries (9 synthetic email retries vs 12). It costs more, is slower and inflates fit scores a little more. Recommendation: effort low for every task.
- **Fit scores inflate on 5.5.** Both 5.5 arms score every synthetic case 5 to 23 points higher than 4.6 on the same inputs (examples from the file: the bait case syn-02 gets 46 for 4.6 against 57 and 66; syn-13 gets 34 against 57 and 62). The Weak, Fair and Strong thresholds will shift. The fit judge scores for grounding sit at 1.3 to 1.6 for both models, so fit is weak evidence either way.

The arm C and fixed-input results came in after Fable's pass and confirm its main suspicion about the prompt confound: the prompts change little, the model does.

## 6. Grounding and hallucination

### Deterministic scorer (`score-*.txt`, 30 kits, rep 1; arm C 16 synthetic kits)

Kits with at least one hit per failure code. F-codes are defined in `evals/README.md`.

| Code | What | 4.6 | 5.5-low | 5.5-medium | Arm C |
|---|---|---|---|---|---|
| F1 | Number not in the CV | 30 | 30 | 30 | 16 |
| F2 | Employer, title or degree not in the CV | 25 | 8 | 10 | 13 |
| F3 | Skill not in the CV | 17 | 5 | 5 | 9 |
| F4 | Claimed a skill the matcher said is missing | 7 | 13 | 12 | 8 |
| F6 | Unknown named entity in prose | 29 | 28 | 29 | 16 |
| F7 | Em dash on raw output | 10 | 0 | 0 | 1 |
| F8 | Voice rules (Oxford comma, filler, blacklist) | 23 | 2 | 3 | 12 |
| F9 | Wrong language | 6 | 6 | 6 | 0 |
| F12 / F14 | Invalid JSON / unclosed | 0 | 3 | 2 | 0 |
| F18 | Production validator miss after retry | 3 | 6 | 2 | 1 |
| Fabrication findings per kit (F1+F2+F3+F5) | | 6.53 | 3.60 | 3.87 | n/a |

Which codes to trust, per Fable and the arm C result:

- **F1 is noise.** Every arm has it on every kit. Nearly all the hits are "12", "2026" (the letter date) and the fit percentage. It carries no signal.
- **F4 is inverted.** 5.5 trips it more because it names the gap honestly ("I haven't worked in Marketo yet", "My background is in Kotlin, Java and Python rather than Go or Rust"). Not one 5.5 hit is a claim. 4.6's hits are mostly honest too, with one soft adjacency claim. Neither model claimed a bait skill.
- **F2 and F3 are partly noise, and real for 4.6.** F2 hits on synthetic cases include "Bachelor of Arts" for "B.A." and a caregiver title for a career break. On owner cases the 5.5 F2/F3 hits are degree equivalents and German translations of skill names. F3 on synthetic cases is real for 4.6 (18 added skills such as "Cross-functional collaboration", "Neukundenakquise") and zero for both 5.5 arms. Arm C kept the problem (F2 13/16, F3 9/16), so it's the model.
- **F7 is prompt-driven.** Plain 4.6 emitted em dashes on 10 of 30 kits, arm C on 1 of 16. The old prompts used em dashes in their own prose and the model copied the habit.
- **F8 is model-driven.** Arm C still breaks the voice rules on 12 of 16 kits (4.6 on production prompts: 23 of 30, 5.5: 2 to 3). Fable guessed part of this was prompts; the arm C data says mostly not.
- **F9 is identical across the three chain arms (6 kits)**, so it's not a model difference. Likely the fit headings that stay in English in every output language by design (`CHANGES.md`, G7). I didn't verify that.
- **F6** is a candidate list (capitalised mid-sentence terms in neither the CV nor the ad), hit on nearly every kit for every arm. Noise at this precision.

### Fable's manual estimate of true substantive fabrications

The judge counts location fields copied from the applicant's city and rephrasings too, so Fable read the quotes:

- **4.6:** about 70% of 30 checked quotes are real. Examples (synthetic): invented outcomes bolted onto real bullets, whole bullets with no source, a certification invented for a course, "Proficient in Google Analytics" for "basic", and a number conflation (a letter said accuracy rose "from 88% to 96% across an 85 million USD business unit" when the CV gives 85M as two units combined). About 30% are inference or judge over-reach.

## 7. Reliability

### Refusals and truncations

Zero. Refusal rate, truncation rate (`stop_reason: max_tokens`) and failed-call rate are 0.00% for all three arms (337 / 319 / 316 calls). Every call in the public (synthetic) arm folders ended with `end_turn`, and `deterministic.json` records zero API-level retries for every arm.

### Production validator misses (F18) and the retries behind them

Each "validation miss" line in the logs is one first-attempt validator failure that triggers a retry. Quality pass, per arm (`log-quality-*.txt`):

| Arm | Misses (30 kits) | Per kit | Most common reason |
|---|---|---|---|
| 4.6 | 37 | 1.23 | Follow-up body over 80 words (23) |
| 5.5-low | 19 | 0.63 | Application email subject over 60 characters (7) |
| 5.5-medium | 16 | 0.53 | Application email subject over 60 characters (6) |
| Arm C (16 kits) | 14 | 0.88 | Application email subject over 60 characters (6) |

Latency reps add 23, 10 and 8 more for 4.6, 5.5-low and 5.5-medium (`log-latency-*.txt`). Breakdown for 5.5-low in the quality pass: email subject over 60 characters 7, follow-up subject over 60 characters 4, email body over four sentences 4, follow-up body over 80 words 2, invalid JSON 2.

So 5.5 passes validation on the first try more often than 4.6 (4.6 over-writes follow-ups). The F18 count after retry is a different story: 4.6 in 3 kits, 5.5-low in 6, 5.5-medium in 2 (chain). Per Fable, first-attempt misses on synthetic emails and follow-ups were 21 of 32 for 4.6, 14 of 32 for 5.5-low, 12 of 32 for 5.5-medium.

### F12 and F14: the root cause is our parser

Fable traced every 5.5 "invalid JSON" output (7 calls). All ended with `end_turn` at 420 to 500 output tokens against `max_tokens` of 4000 to 4096, so none was truncation. Each is a complete JSON object, then a line like "Wait, the subject must be 60 characters or fewer. Corrected output:", then a second JSON object with a shorter subject. `parseStrictJsonObject` in `src/lib/agents/unified-writer-agent.ts` matches `/\{[\s\S]*\}/`, which is greedy and spans the first brace to the last, so it swallows both objects and `JSON.parse` fails. F14 is the same event as the scorer sees it.

The trigger is the 60-character subject cap. 5.5 follows instructions literally, catches its own violation after emitting the JSON, and self-corrects in the text. The ad title is often long: 9 of 16 first-attempt subjects were 61 to 79 characters. The model is doing the right thing and the parser punishes it. The fixes are in section 9. Also noted by Fable: the "four sentences" counter splits on every period, so a body with "Google Analytics (basic)." miscounts, a validator bug that affects both models.

By the decision rule's strict wording ("zero JSON failures") 5.5 does not pass until the parser is fixed. That is a production code fix, not a model weakness.

## 8. Limitations

- **One real applicant CV.** All 14 owner cases share one CV. Synthetic CVs are six constructed people. Results on other real CVs aren't measured.
- **Judge bias.** One judge family (Opus 5.5) wrote almost every verdict, and the rubric makes any fabrication decisive. The CV and letter sweeps are grounding verdicts, and the letter result is partly length-driven (section 5). The second-vendor re-judge agreed on 23 of 24, but it covers 24 synthetic pairs of one comparison.
- **Small sample.** 30 cases, 1 quality rep. Latency has 20 kits per arm. A tie rate of 0 to 7 of 30 per document means single flips matter little at 30-0, but they matter in the email and fit tables.
- **Few German cases.** 6 of 30 (4 owner, 2 synthetic). Fable found a broken German sentence in one 5.5 letter and judged the German letter better for 4.6 on prose.
- **The prompts differed between arms.** Arm A ran production prompts and the 5.5 arms ran tuned ones, with three plain bug fixes in them. Arm C (4.6 on the new prompts, 16 synthetic kits, judged against 5.5-low only) shows the prompts account for the em-dash gap and a little of email and fit, and not for the CV, letter or fabrication gaps. Arm C wasn't judged against plain 4.6 directly, and it wasn't run on owner cases.
- **`skill_matching` prompt weakness.** It marks bait requirements as claimable on every arm. It feeds both the fit text and the letter allow-list. It wasn't changed in this eval.
- **Fit score inflation.** 5.5 scores 5 to 23 points higher than 4.6 on the same input, so the fit thresholds need recalibrating.
- **Latency reps.** 10 cases, 4 of them owner. They don't separate cold start from steady state, and API latency drifts by time of day. The three arms ran sequentially in separate windows (2,987 s, 1,072 s and 1,193 s wall clock).
- **Costs are computed from usage at list prices**, not read from an invoice.
- **Owner blind review:** done by the owner on 2026-10-12 (10 kits). Its notes aren't recorded in this file.

## 9. Conclusion and decision

Against the decision rule:

| Rule | Result |
|---|---|
| 5.5 wins or ties on writing | Wins on the judge tables (grounding-driven). Roughly even on Fable's manual writing read. Not worse. |
| Fabrication not higher | Much lower: judge quotes 5.3 to 6.0 vs 16.1 to 16.6 per kit; Fable's estimate 1 to 2 vs 8 to 10 substantive per kit. |
| Zero truncations, refusals, JSON failures | Zero truncations and refusals. JSON failures exist but trace to the greedy-regex parser, fixable in our code. |
| p95 kit latency within +25% | p95 is 61% lower (69.5 s vs 178.1 s). |
| Cost per kit not higher | 23% lower. |

**Decision: switch the production kit and CV parsing to Sonnet 5.5, adaptive thinking, effort low for every task.** Medium buys nothing measurable on the documents that matter and adds latency and score inflation. The core evidence isn't the 30-0 tables. It's that 5.5's CVs contain no invented skills, titles or numbers on the synthetic cases while every 4.6 CV does, that this holds with 4.6 on the new prompts (arm C) and on identical inputs, that a second vendor's judge agrees, and that 5.5 is 2 to 3 times faster at lower cost.

Conditions for the production change (from the analysis and arm C):

1. Port the `sonnet55` prompt changes to production. At least the three plain bugs (CV schema trailing comma, "Job Copilot" name, dangling "Rule 4d") and the em-dash cleanup help whichever model runs.
2. Use `output_config.format` with a JSON schema on every JSON task, in particular `write_email` and `write_follow_up_email`. If that's not done, replace the greedy regex with a balanced-brace scan that takes the last object that parses (the self-corrected one). Verify by replaying the 7 failing raw outputs.
3. Build the application email subject in code (or raise the 60-character limit) so the model doesn't self-correct at the cap.
4. Effort low, adaptive thinking, no temperature, `max_tokens` as in `evals/lib/arms.ts`.
5. Add a gap-handling rule to the letter and email prompts: transferable experience only, no "I haven't" or "won't pretend" sentences, or at most one.
6. Recalibrate the fit thresholds against the 5.5 score distribution (about +10 points on the same inputs).
7. Watch in production: availability and start-date lines in emails (the one fabrication class 5.5 has), and the retry rate per email task after the parser change.
